# Googleアカウント・Drive同期（Issue #42）

設定の「アカウント・同期」からGoogleでログインし、Driveのアプリ専用領域を使って予定を同期します。既存の端末内データはそのまま利用でき、同期しない場合はGoogleアカウント不要です。

## 開発者の初回設定

予定館用のiOSクライアントIDは `ios/Google.xcconfig` に設定済みです。バンドルIDは `org.sfuji.yoteikan` です。そのままビルドできます。以下の手順6は、別のGoogle Cloudプロジェクトを使用する場合の上書き設定です。OAuthクライアントIDは公開識別子であり、秘密鍵ではありません。

1. [Google Cloud Console](https://console.cloud.google.com/)で予定館用のプロジェクトを作成します。将来Web版を作る際も同じプロジェクトを使用します。
2. APIライブラリで **Google Drive API** を有効にします。
3. Google Auth Platformでアプリ名・サポートメール・対象ユーザーを設定します。個人のGoogleアカウントで試す場合は外部向けとし、テスト中は使用するGoogleアカウントをテストユーザーへ追加します。
4. アクセス権限に `https://www.googleapis.com/auth/drive.appdata` を追加します。Drive全体への読み書き権限は不要です。Google Sign-Inがログインに必要な基本プロフィールの権限も取得します。
5. OAuthクライアントを **iOS** として作成し、バンドルIDを **`org.sfuji.yoteikan`** に設定します。App Store IDは未配信なら空欄で構いません。Web用・デスクトップ用クライアントをiOS用の代わりに使用しないでください。
6. 発行されたクライアントIDを使い、リポジトリのルートで次を実行します。

```sh
go run ./tools/google-config/main.go \
  --client-id YOUR_IOS_CLIENT_ID.apps.googleusercontent.com
```

`ios/Google.local.xcconfig` が作成され、クライアントIDと逆順のURLスキームを設定します。`ios/Google.xcconfig` 経由でDebug・Releaseの両方に反映されます。ローカル設定ファイルはGit管理対象外です。クライアントシークレットは使用せず、アプリに埋め込みません。

7. `ios/Yoteikan.xcodeproj` をXcodeで開き、Swift Packageの解決が終わるのを待ちます。Google公式のGoogleSignInを使用し、依存バージョンは `Package.resolved` に記録しています。
8. 実機用のDevelopment Teamを設定し、ビルド・起動します。設定 → アカウント・同期 → Googleでログインから、手順3のアカウントを使用してアクセスを許可します。

CIからは `GOOGLE_CLIENT_ID` と `GOOGLE_REVERSED_CLIENT_ID` をXcodeのビルド設定として渡す方法も使えます。両者が一致しない場合はログインを開始せず、設定が未完了であることを表示します。

公式資料：[iOSへの導入](https://developers.google.com/identity/sign-in/ios/start-integrating) / [Google APIへのアクセス](https://developers.google.com/identity/sign-in/ios/api-access) / [アプリ専用領域](https://developers.google.com/workspace/drive/api/guides/appdata)

## 利用者の操作

- 初回はログイン後に、同期するデータを選びます。選択前にはアップロードしません。
- Driveにデータがなければ「このiPhoneの予定で同期を開始」を選びます。
- 既存データがあれば「クラウドの予定を使う」または「このiPhoneの予定も追加する」を選べます。追加する場合、同じ項目への異なる変更は競合として表示します。
- 同期開始前の端末データは復元用に保存します。復元ボタンを押すと確認画面を出し、ログイン中なら復元による変更も同期対象になります。
- 起動・フォアグラウンド復帰時と、編集から約2秒後に同期します。「今すぐ同期」でも実行できます。iOSがアプリを停止している間の常時同期は行いません。
- 最終同期時刻、未送信の変更件数、エラー、競合する内容を画面で確認できます。通信できない場合も端末側への保存は続き、再試行時に送信します。
- ログアウトしても端末とDriveのデータは削除しません。別アカウントでログインした場合も、改めてデータを選ぶまで端末の予定を送信しません。

## 同期する範囲

付箋の内容・所要時間・開始時刻・日付・色・保存済みメモ・通知の何分前設定、プリセットと毎日の枚数、計画の時間帯、パレット、毎日の自動追加の記録を同期します。

iPhoneカレンダーから取り込んだ固定予定とメモ、OSの通知・カレンダー権限、Googleの認証情報、サイドバーの左右・拡大率、未保存のメモ下書きは送信しません。Googleのトークン管理・更新・ログアウトは公式SDKに任せます。

バンドルIDは `org.sfuji.yoteikan`、テストはその `.YoteikanTests` / `.YoteikanUITests` です。旧ID `com.sota.yoteikan` とはOS上で別アプリになるため、旧アプリの端末内データは自動移行されません。旧IDのアプリを削除する処理は行っていません。

## 同時編集と通信失敗

Drive上で同じファイルを上書きする代わりに、変更をまとめたJSONを新しいファイルとして追加します。アプリ専用領域の `appProperties` が `yoteikan=sync-v1` のファイルだけを列挙し、ページ送りも処理します。一度取得したファイルはアカウント別の取得済み記録を使って再取得を省きます。

各変更には対象のキー・値・直前の変更IDを保存し、その内容のSHA-256をIDとします。再送で同じファイルが重複しても変更は一度だけ反映します。異なる付箋への変更は統合し、同じ項目への同時編集や削除との衝突は候補を残して、利用者が残す内容を選びます。選択結果も同期します。毎日の生成済み枚数は大きい方を採用し、新規自動付箋のIDも日付・プリセット・枚数から決めることで二重生成を防ぎます。

送信中に追加編集があっても、その変更を送信済み扱いにはしません。通信・権限・形式エラーの場合はエラーを表示し、未送信の変更を保持します。アカウントごとの履歴は端末内に保存し、アカウントの切り替えで使い回しません。Driveから同期ファイルがすべて削除されていた場合、接続済み端末の同期操作では端末の履歴を再送します。項目を削除して他端末にも反映したい場合はアプリ内で削除してください。

ファイル形式はバージョン1です。未知のバージョンや不正な項目は取り込みを中断します。現在は履歴の圧縮・自動削除を行わないため、長期利用では履歴量に応じて初回取得時間が増えます。Webから同じ形式で閲覧・編集する環境は [Web版の起動・公開手順](web.md) を参照してください。

## 検証と実接続で残る確認

提供されたiOSクライアントIDと対応するコールバックURLを設定し、ビルドを確認しました。実際のGoogleアカウントでの認証・実Driveへのアップロード・別の実機間での同期は、利用者によるログイン・アクセス許可を伴うため未確認です。次の順で確認してください。

1. 端末AでGoogleログインし、初回のデータ選択後に同期できること。
2. 同じGoogle Cloudプロジェクトの同じバンドルIDでビルドした端末Bから、同じアカウントでログインし、クラウドの予定を読み込めること。
3. Aで付箋を変更・削除し、Bの「今すぐ同期」で反映されること。
4. 両端末をオフラインにして同じ付箋を編集し、接続後に競合の候補と選択結果を確認すること。
5. Google側でアクセスを取り消した際にエラーを表示し、再ログインで復帰できること。
6. ログアウト後・別アカウントへの変更時に、端末データを勝手に送信しないこと。

自動テストではメモリー上のDrive代替、HTTPレスポンス代替、シミュレーター専用の画面確認用アカウントを使用します。画面確認用のログインは本物のGoogle接続ではなく、Releaseビルドには含めません。

### 将来のWebクライアント向けの形式

バッチは `{"version":1,"mutations":[...]}`、変更は `key`・`parents`・`value` で構成します。キーは `sticky/UUID`、`preset/UUID`、`daily/YYYY-MM-DD`、`hours`、`colors` です。`value` はその項目のJSONバイト列をBase64にした文字列で、削除時には省略します。`parents` は同じ項目で観測した先端の変更IDを辞書順に並べた配列です。

変更IDは、変更のキーを辞書順に並べ、空白なし・スラッシュのエスケープなし・UTF-8でJSON化した内容のSHA-256（小文字16進数）です。ID自体は変更内に含めません。同じ内容の初期変更は端末をまたいでも同じIDになります。Web版も同じ正規化とデータ選択・競合解決を実装する必要があります。
